<h1>Codex 多 Agent 协作实际 Prompt 模板</h1>
<ul>
<li>目标: 给出适合 Codex 使用的、可直接复制粘贴的多 agent 协作 prompt 模板</li>
<li>适用场景: 复杂编码任务、长任务排障、跨模块实现、代码库梳理后再动手的大任务</li>
<li>使用前提: 你已经明确允许 Codex 启用多个 agent，并且任务存在可并行拆分空间</li>
</ul>
<hr>
<h2>1. 先讲清楚这份模板解决什么问题</h2>
<p>这份模板主要解决 5 个常见问题:</p>
<ol>
<li>主 agent 不知道该怎么拆任务</li>
<li>多个子 agent 容易改到同一批文件，互相打架</li>
<li>explorer 只会读代码，但无法沉淀成可执行结论</li>
<li>worker 做完局部改动后，主线程不会整合和收口</li>
<li>验证和集成阶段经常被省略，最后交付只有“改了一些东西”</li>
</ol>
<p>所以这份模板会把协作拆成 5 类角色:</p>
<ul>
<li>主控 Orchestrator</li>
<li>事实探查 Explorer</li>
<li>实现 Worker</li>
<li>验证 Verifier</li>
<li>集成 Integrator</li>
</ul>
<hr>
<h2>2. 推荐协作结构</h2>
<pre><code>flowchart TD
    A[&#34;用户需求&#34;] --&gt; B[&#34;主控 Orchestrator\n读取代码库并拆任务&#34;]
    B --&gt; C[&#34;Explorer\n补充代码事实与约束&#34;]
    B --&gt; D[&#34;Worker A\n负责模块 A&#34;]
    B --&gt; E[&#34;Worker B\n负责模块 B&#34;]
    B --&gt; F[&#34;Verifier\n准备验证路径&#34;]
    C --&gt; B
    D --&gt; G[&#34;主控整合结果&#34;]
    E --&gt; G
    F --&gt; G
    G --&gt; H[&#34;Integrator\n统一修边、跑验证、收口&#34;]
    H --&gt; I[&#34;最终交付&#34;]
</code></pre>
<hr>
<h2>3. 多 Agent 协作的固定规则</h2>
<p>下面这些规则建议无论什么任务都写进主控 prompt。</p>
<h3>3.1 任务拆分规则</h3>
<ul>
<li>只有当子任务彼此独立、可并行时，才拆给多个 agent</li>
<li>若某个子任务是“下一步必须立即依赖的关键路径”，优先由主线程自己做</li>
<li>每个 worker 必须有明确的文件所有权或模块边界</li>
<li>不允许两个 worker 同时改同一文件，除非主控明确安排串行接力</li>
</ul>
<h3>3.2 协作规则</h3>
<ul>
<li>explorer 负责回答具体问题，不负责大面积写代码</li>
<li>worker 负责在明确边界内产出代码，不负责全局收口</li>
<li>verifier 负责验证与复现，不负责定义产品范围</li>
<li>integrator 负责统一检查、补缝、跑最终验证</li>
</ul>
<h3>3.3 交接规则</h3>
<ul>
<li>每个 agent 完成后都要交付简短结论</li>
<li>若有代码改动，必须说明改了哪些文件</li>
<li>若有未完成项，必须写清楚阻塞点和下一步建议</li>
<li>主控不能直接照抄子 agent 结论，必须做整合判断</li>
</ul>
<h3>3.4 质量规则</h3>
<ul>
<li>不允许把“已分析”当作“已完成”</li>
<li>不允许把“理论上可行”当作“已验证”</li>
<li>不允许把 stub、占位 UI、假数据链路说成完成</li>
<li>不允许省略最终整合验证</li>
</ul>
<hr>
<h2>4. 主控 Orchestrator Prompt 模板</h2>
<p>这是最核心的一段。适合直接发给 Codex 主线程。</p>
<pre><code>你是本次任务的主控 Codex，需要在必要时启用多个 agent 协作完成任务。

任务背景:
&lt;在这里写项目、目录、需求背景&gt;

本次目标:
&lt;在这里写最终要交付的结果&gt;

完成标准:
- &lt;标准 1&gt;
- &lt;标准 2&gt;
- &lt;标准 3&gt;

工作方式:
1. 先阅读代码库和关键文件，确认真实现状，不要凭印象开工。
2. 判断任务中哪些部分适合并行，哪些部分必须由主线程自己处理。
3. 只把独立、边界清晰、可并行的子任务交给子 agent。
4. 给每个子 agent 明确的职责、输入、输出、文件边界和验证目标。
5. 不允许多个 worker 同时修改同一文件。
6. explorer 只负责回答具体代码库问题，不负责大面积实施。
7. worker 完成后，主线程要负责整合、补缝、验证和最终收口。
8. 若发现任务并不适合多 agent，及时收缩为主线程执行，不要为了拆而拆。

输出要求:
- 先给出一个简短计划
- 再开始阅读、拆分、执行
- 实施过程中持续汇报进度
- 最终交付时说明:
  - 实际做了什么
  - 哪些工作由子 agent 完成
  - 如何验证
  - 还剩哪些风险

注意:
- 不要停留在分析层
- 以真实代码、真实命令、真实验证为准
- 目标是闭环交付，而不是只生成建议
</code></pre>

<h2>5. Explorer Prompt 模板</h2>
<p>适合“先问清代码库事实，再决定怎么改”的场景。</p>
<pre><code>你是 Explorer，只负责回答一个具体、边界清晰的代码库问题。

问题:
&lt;在这里写要探查的问题&gt;

你的任务:
- 阅读相关代码、配置、测试、脚本
- 给出基于真实文件的事实结论
- 标出关键文件与关键逻辑位置
- 总结与当前主任务最相关的约束和风险

输出格式:
1. 结论
2. 证据
3. 关键文件
4. 风险或不确定点
5. 对主线程的建议下一步

限制:
- 不要泛泛解释
- 不要写与问题无关的大段综述
- 不要做大面积代码修改，除非主线程明确授权
</code></pre>
<h3>5.1 Explorer 实用示例</h3>
<pre><code>你是 Explorer，只回答一个问题:

请检查当前仓库里“用户注册完成后跳转到工作台”的链路实际由哪些文件控制。

要求:
- 找出前端触发点
- 找出后端返回字段
- 找出路由跳转条件
- 找出测试覆盖情况
- 判断为什么当前会停留在注册页

输出:
1. 根因候选
2. 证据文件和关键函数
3. 修复建议，但不要直接实施
</code></pre>
<hr>
<h2>6. Worker Prompt 模板</h2>
<p>适合交给具体实现 agent。</p>
<pre><code>你是 Worker，负责一个边界清晰的实现子任务。

任务:
&lt;在这里写具体实现目标&gt;

你负责的文件或模块范围:
- &lt;文件/目录 1&gt;
- &lt;文件/目录 2&gt;

你不负责的范围:
- &lt;不该碰的文件或模块&gt;

完成标准:
- &lt;标准 1&gt;
- &lt;标准 2&gt;

工作要求:
- 先阅读你负责范围内的现状，再动手修改
- 只在自己负责的范围内实施
- 不要回滚别人已存在的改动
- 不要扩大任务边界
- 若发现依赖主线程处理的阻塞，明确写出
- 完成后说明你改了什么、为什么这样改、如何验证

输出要求:
1. 已完成改动
2. 修改文件列表
3. 验证结果
4. 未完成项或阻塞
</code></pre>
<h3>6.1 Worker 实用示例</h3>
<pre><code>你是 Worker，负责注册流程中的“成功后跳转工作台”前端部分。

你的负责范围:
- frontend/src/pages/register/**
- frontend/src/router/**
- frontend/src/stores/auth/**

你不负责:
- 后端接口语义调整
- 数据库结构修改
- 其他无关页面

完成标准:
- 注册成功后，前端依据真实返回状态完成跳转
- 保持现有错误提示逻辑不退化
- 补至少一条与跳转相关的前端测试或说明当前只能做 smoke 验证

输出:
1. 改动摘要
2. 修改文件
3. 验证方式
4. 仍需主线程配合的点
</code></pre>

<h2>7. Verifier Prompt 模板</h2>
<p>适合让子 agent 专门负责“设计验证路径”或“复测改动是否真的生效”。</p>
<pre><code>你是 Verifier，负责验证当前实现是否满足目标。

验证目标:
&lt;在这里写要验证的目标&gt;

验证范围:
- UI 行为
- API 行为
- 数据状态
- 构建或测试状态

你的任务:
- 不要假设功能正常，要主动找反例
- 先列出验证清单
- 再执行最关键的验证
- 报告通过项、失败项、未验证项

输出格式:
1. 验证清单
2. 已执行验证
3. 通过项
4. 失败项
5. 未验证项
6. 总体结论: PASS / FAIL
</code></pre>
<h3>7.1 Verifier 实用示例</h3>
<pre><code>你是 Verifier。

请验证“注册成功后自动跳转到工作台”这项改动是否真正成立。

至少覆盖:
- 注册接口返回成功时，页面是否跳转
- 返回部分成功/待补全状态时，页面是否进入正确分支
- 刷新页面后状态是否一致
- 是否存在 UI 提示与实际路由状态不一致的问题

输出:
1. 复现路径
2. 通过项
3. 失败项
4. 风险点
5. PASS / FAIL
</code></pre>
<hr>
<h2>8. Integrator Prompt 模板</h2>
<p>适合主线程或专门收口 agent 在最后阶段使用。</p>
<pre><code>你是 Integrator，负责把多个子 agent 的结果整合为可交付结果。

输入:
- Explorer 结论
- Worker 改动
- Verifier 报告

你的任务:
- 检查各子任务之间是否存在边界缝隙
- 处理接口拼接、类型不一致、命名不一致、验证遗漏等问题
- 跑最终构建、测试或 smoke 验证
- 给出最终交付说明

要求:
- 不要只是拼接结果
- 要主动发现并修补集成问题
- 若某个子任务虽完成局部目标，但整体仍未闭环，要明确指出

输出:
1. 集成后状态
2. 新补的改动
3. 最终验证
4. 风险与未覆盖项
</code></pre>

<p>这一段适合你在复杂 coding 任务里直接发给 Codex。</p>
<pre><code>你现在作为主控 Codex，必要时请启用多个 agent 协作完成任务。

任务:
&lt;在这里写完整任务&gt;

环境:
- 工作目录: &lt;路径&gt;
- 技术栈: &lt;技术栈&gt;
- 关键约束: &lt;约束&gt;

完成标准:
- &lt;标准 1&gt;
- &lt;标准 2&gt;
- &lt;标准 3&gt;

请按以下方式工作:
1. 先阅读代码库，确认现状、关键文件、现有测试与风险。
2. 判断任务是否适合多 agent；如果适合，只拆分独立且可并行的子任务。
3. 优先把“事实探查”和“独立模块实现”并行化，不要把关键阻塞路径完全外包。
4. 给每个子 agent 明确边界:
   - 任务目标
   - 负责文件或模块
   - 不负责范围
   - 输出格式
5. 不允许多个 worker 修改同一文件。

7. 如果子 agent 结果与代码库现状冲突，以真实代码和验证结果为准。
8. 最终不要只停在建议层，必须形成实际交付。

最终回复必须包含:
- 改了什么
- 哪些工作由哪个子 agent 完成
- 如何验证
- 还剩哪些风险
</code></pre>

<h2>10. 三个高频任务的即用型 Prompt</h2>
<p>下面是最常用的三种即用版本。</p>
<h3>10.1 功能开发型</h3>
<pre><code>你现在作为主控 Codex，必要时启用多个 agent 协作实现一个复杂功能。

任务:
请在当前仓库中实现: &lt;功能需求&gt;

请遵循以下流程:
1. 先阅读需求相关代码与测试，识别真实约束。
2. 将任务拆为:
   - 代码事实探查
   - 前端实现
   - 后端实现
   - 验证与收口
3. 仅在文件边界清晰时并行启用子 agent。
4. 每个子 agent 必须有独立职责和文件边界，避免重叠修改。
5. 主线程负责关键接口对齐、最终集成与验证。

完成标准:
- 功能主路径真实可用
- 至少完成关键验证或补充测试
- 不把 stub 或占位实现当完成
- 最终给出清晰交付说明
</code></pre>
<h3>10.2 排障修复型</h3>
<pre><code>你现在作为主控 Codex，必要时启用多个 agent 协作定位并修复问题。

问题:
&lt;Bug 描述&gt;

要求:
1. 先确认问题能否复现，收集真实错误信息。
2. 可并行拆出:
   - Explorer: 查找相关链路、日志、代码路径
   - Worker: 在明确根因后实施修复
   - Verifier: 复测修复是否生效
3. 在根因不明前，不要盲目大改。
4. 修复后必须有验证证据。

完成标准:
- 问题根因明确
- 修复已落地
- 关键复测通过
- 无明显副作用未说明
</code></pre>
<h3>10.3 大型重构型</h3>
<pre><code>你现在作为主控 Codex，必要时启用多个 agent 协作完成一次受控重构。

目标:
&lt;重构目标&gt;

约束:
- 不改变对外行为
- 不引入无关改动
- 需要保留现有测试或补最小必要验证

工作方式:
1. 先由 Explorer 梳理现有结构、依赖与风险点。
2. 再拆分为若干不重叠的重构子任务，每个 worker 只负责一个切片。
3. 主线程负责公共接口对齐与最终集成。
4. Verifier 负责确认行为不回退。

完成标准:
- 结构目标达成
- 对外行为未退化
- 改动边界清晰
- 有最终验证说明
</code></pre>

<h2>13. 最适合写进 Prompt 的硬规则</h2>
<p>如果你希望 Codex 多 agent 协作更稳，建议把下面这些句子直接写进 prompt。</p>
<h3>13.1 文件边界规则</h3>
<pre><code>每个 worker 必须有明确文件边界，不允许多个 worker 同时修改同一文件。
</code></pre>
<h3>13.2 主线程责任规则</h3>
<pre><code>主线程必须负责最终集成、验证和收口，不能把最终交付责任外包给子 agent。
</code></pre>
<h3>13.3 验证规则</h3>
<pre><code>任何实现都不能只停在“代码已修改”，必须说明如何验证以及验证结果。
</code></pre>
<h3>13.4 反重叠规则</h3>
<pre><code>若两个子任务边界不清晰，则不要并行拆分，改由主线程串行推进。
</code></pre>
<h3>13.5 反空转规则</h3>
<pre><code>explorer 必须回答具体问题，worker 必须交付具体改动，verifier 必须给出 PASS/FAIL，避免空泛总结。
</code></pre>
<hr>
<h2>14. 什么时候不该启用多 Agent</h2>
<p>下面这些情况通常不适合硬拆多 agent:</p>
<p>| 情况 | 原因 |
| --- | --- |
| 修改只集中在 1 到 2 个文件 | 并行收益很低 |
| 下一步强依赖单一结论 | 主线程自己做更快 |
| 任务边界很模糊 | 容易拆乱、改重叠 |
| 只是读一个文档然后产出总结 | 没必要上多 agent |
| 代码库极小 | 并行成本往往高于收益 |</p>

目标:
&lt;任务目标&gt;

完成标准:
- &lt;标准 1&gt;
- &lt;标准 2&gt;

工作要求:
1. 先读代码库确认现状。
2. 只把独立、可并行、边界清晰的子任务拆给子 agent。
3. Explorer 负责查事实，Worker 负责做实现，Verifier 负责做验证。
4. 不允许多个 worker 同时改同一文件。
5. 主线程负责关键路径、结果整合、最终验证和收口。
6. 最终必须交付实际结果，而不是只给建议。
</code></pre>

<h2>16. 最后的使用建议</h2>
<p>如果你希望这套模板真正好用，我建议记住下面 4 条:</p>
<ol>
<li>多 agent 的收益来自“并行解决独立问题”，不是来自“把一个问题拆得很碎”。</li>
<li>主控 prompt 一定要写清楚文件边界，否则最容易互相覆盖。</li>
<li>explorer、worker、verifier 的输出格式最好固定，不然主线程很难整合。</li>
<li>最终质量往往取决于主线程的集成和验证，而不是子 agent 数量。</li>
</ol>
