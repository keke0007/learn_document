# 上下文、提示词与端点学习计划

## 这条学习线的真实目标

这条学习线不是为了理解 `oh-my-opencode` 的项目架构，也不是为了记住哪个文件做了什么。

真正目标是：

- 借这个项目的实现，理解一个多 Agent / Tool / Skill 系统里，上下文是怎么被组织、裁剪、拼装、传递的
- 理解首轮对话、工具调用轮、Skill 注入轮、子 Agent 轮、多轮长对话轮，这几类典型场景在 LLM endpoint 上大概会长成什么样
- 最终达到：看到一个页面的输出形态，能大致反推出背后可能发生了几次调用、每次调用上下文里大概有什么

所以，这份计划是“数据结构与上下文编译”导向，而不是“源码文件导览”导向。

## 学习方法

我们不按模块学，而按“上下文如何被编译成一次 LLM 调用”来学。

每一章都围绕三个层次：

1. 抽象层
   - 这个阶段到底在解决什么上下文问题
2. 数据结构层
   - 这一层有哪些对象，字段是什么，哪些会被拼进 endpoint
3. 运行时层
   - 首轮、多轮、工具、skill、子 Agent 场景下，payload 会怎么变化

项目源码只作为证据，不作为主线。

## 核心原则

- 少讲文件，多讲对象
- 少讲“某个 hook 做了什么”，多讲“为什么上下文必须分层”
- 每章最后都要能写出一个近似的 endpoint payload 示例
- 每一章都必须落到“最终 LLM endpoint 请求体”
- 每一章都必须给出一个 OpenAI spec 风格的 mock 请求体
- 每一个概念都必须能回到这个项目的代码证据
- 每章都要能回答：
  - 首轮调用是什么
  - 中间轮调用是什么
  - 长对话后的调用为什么会变形

## 练习方式

这条学习线默认采用“做中学”的方式推进。

每一章都必须同时产出 3 个东西：

1. 概念解释
   - 这一章的上下文问题是什么
2. 项目证据
   - 这个项目里哪些实现可以证明这种拼装方式存在
3. mock 请求体
   - 用 OpenAI spec 风格写出一个可直接用于练习的请求体

默认练习方式：

- 使用 OpenAI spec 风格模型
- 支持 tools / tool calls / 多轮 messages
- 用 mock 的 endpoint 请求体帮助理解上下文是怎么被编译出来的

注意：

- 这里的 mock 请求体是“教学用近似结构”
- 它的目标是帮助理解上下文编译逻辑
- 不等于声称这个项目最终对 provider 的真实请求体 100% 就是这个样子
- 我们会明确区分：
  - 代码已证明
  - 基于 OpenAI spec 的教学映射

## 统一抽象模型

后续所有章节，都统一落到这几个核心对象上理解：

### 1. 会话状态 `ConversationState`

表示某一时刻，一个 Agent 真正“拥有”的上下文总和。

建议用这个抽象去理解任何框架：

```ts
type ConversationState = {
  session_id: string
  active_agent: string
  visible_history: Message[]
  hidden_system_layers: ContextChunk[]
  working_memory?: SummaryBlock
  tool_schemas: ToolSchema[]
  tool_results: ToolResultBlock[]
  skill_context: SkillBlock[]
  subagent_artifacts: SubagentArtifact[]
  provider_options: ProviderOptions
}
```

### 2. 一次调用 `CompiledPrompt`

表示“从当前状态中挑哪些东西，真正送去调用模型”。

```ts
type CompiledPrompt = {
  model: string
  system?: string
  messages?: ProviderMessage[]
  tools?: ToolSchema[]
  stream?: boolean
  extra?: Record<string, unknown>
}
```

### 3. 一次返回 `TurnOutput`

表示一次模型调用后，返回了什么，以及哪些内容要重新写回会话状态。

```ts
type TurnOutput = {
  assistant_message?: Message
  tool_calls?: ToolCall[]
  tool_results?: ToolResultBlock[]
  new_memory?: SummaryBlock
  render_events?: RenderEvent[]
}
```

### 4. 子 Agent 工件 `SubagentArtifact`

表示子 Agent 不把完整内部历史暴露给主 Agent，而是折叠成一个可回注的结果块。

```ts
type SubagentArtifact = {
  session_id: string
  agent: string
  task: string
  result_text: string
  metadata?: Record<string, unknown>
}
```

后面每一章都要回答：这些对象在该阶段如何变化。

## 章节安排

### 第 0 章：统一消息模型

核心问题：

- 无论用 OpenCode、LangGraph，还是 Java 手写，最小可用的上下文对象集合是什么？

本章重点：

- 区分 `visible history`、`hidden context`、`memory`、`tool result`、`subagent artifact`
- 区分“会话状态”和“一次 endpoint payload”
- 区分“页面渲染看到的内容”和“真正送给模型的内容”

本章目标：

- 建立统一抽象词汇表
- 后续所有实现都映射到这套词汇
- 给出一个最小可用的 OpenAI spec mock 请求体骨架

### 第 1 章：首轮对话的 endpoint 结构

核心问题：

- 用户第一次发消息时，一次完整的 LLM 调用上下文由哪些层组成？

必须讲清楚：

- system prompt
- developer / rules / hidden instructions
- 用户消息
- tools schema
- 可选 skill 注入
- provider 参数

本章产物：

- 一个“首轮调用”的标准 payload 模板
- 一个“如果有 tool / skill / category 限制时”的变体模板
- 至少一个完整的 OpenAI spec mock 请求体

### 第 2 章：工具调用轮的上下文变化

核心问题：

- 当模型调用了工具，工具结果是如何回到下一轮上下文里的？

必须讲清楚：

- 模型输出的 tool call
- 运行时执行工具
- 工具结果的结构
- 工具结果如何变成下一轮模型上下文的一部分
- 工具结果如何同时影响页面渲染

本章产物：

- 一套“调用工具前 / 工具后 / 再次请求模型”的三段式 payload 示例
- 包含 tool schema、assistant tool call、tool result 回注的 OpenAI spec mock 示例

### 第 3 章：Skill 的两种本质

核心问题：

- Skill 到底是“预置提示词包”还是“运行时工具结果”？

必须讲清楚两种路径：

1. 作为 system / hidden context 注入
2. 作为工具返回值提供给当前 Agent

本章产物：

- 两套 payload 例子：
  - skill 作为注入上下文
  - skill 作为工具返回文本
- 两套 OpenAI spec mock 请求体

### 第 4 章：子 Agent 的上下文合同

核心问题：

- 主 Agent 调子 Agent 时，父上下文会传多少？子 Agent 的结果又以什么形式回到主 Agent？

必须讲清楚：

- 父 Agent 传给子 Agent 的最小必要上下文
- 为什么不能把父会话全量转发
- 子 Agent 自己内部可能有多轮调用
- 主 Agent 最终通常只接收折叠后的结果块，而不是子会话全历史

本章产物：

- 一个“父 -> 子 -> 父”的标准合同模板
- 一个同步返回例子
- 一个异步 / background 返回例子
- 父 Agent 与子 Agent 的两套 OpenAI spec mock 请求体

### 第 5 章：长对话、裁剪、摘要与 Memory

核心问题：

- 对话到了十几轮、几十轮以后，为什么 endpoint payload 不可能还是完整原文？那它会变成什么？

必须讲清楚：

- 最近若干轮原文
- 更早历史的 summary / memory
- 哪些内容必须保留原文
- 哪些内容可以折叠
- tool result 和 subagent result 在长对话中如何保留

本章产物：

- 三个 payload 模板：
  - 第 1 轮
  - 第 8 轮
  - 第 30 轮
- 三个对应的 OpenAI spec mock 请求体

### 第 6 章：从页面输出反推调用链

核心问题：

- 看到一个页面的最终渲染结果，如何反推它背后大概发生了什么调用？

必须讲清楚：

- 文本块、thinking、tool result、toast、warning 分别意味着什么
- 哪些 UI 内容说明“这一轮只调用了一次模型”
- 哪些 UI 内容说明“中间发生了工具调用”
- 哪些 UI 内容说明“调用了子 Agent”
- 哪些 UI 内容说明“做过裁剪 / memory 注入 / continuation”

本章产物：

- 一套逆向判断表
- 三个真实场景演练：
  - 普通问答
  - 工具增强问答
  - 子 Agent 协作问答
- 每个场景都反推出至少一个近似请求体

### 第 7 章：映射到 LangGraph / Java 手写实现

核心问题：

- 如果不用这个项目，而是自己用 LangGraph 或 Java 手写，应该保留哪些核心设计？

必须讲清楚：

- 哪些数据结构必须自己显式建模
- 哪些上下文拼接逻辑不能偷懒
- 哪些东西适合框架帮你做
- 哪些东西必须你自己掌控

本章产物：

- 一套框架无关的实现清单
- 一个最小可用 Agent runtime 数据结构草图

## 为什么这样改

当前最关键的不是“这个项目有哪些模块”，而是你要建立下面这个能力：

- 能手工写出一个首轮 payload
- 能手工写出一个工具调用后的下一轮 payload
- 能手工写出一个子 Agent 返回主 Agent 后的下一轮 payload
- 能手工写出一个几十轮对话后被裁剪过的 payload

只有做到这一层，后面不管用 LangGraph 还是 Java 手写，你都能自己设计上下文系统。

## 与当前仓库的关系

这个仓库仍然是我们的主要参考样本，但使用方式变了：

- 以前：按文件和模块理解项目
- 现在：按“上下文编译问题”去拿这个项目举例

也就是说：

- 源码是证据
- 统一数据模型才是主线
- OpenAI spec mock 是教学载体

## 证据标准

后续每一章都必须遵守下面这个证据标准：

1. 先讲抽象
   - 例如 system、tool、skill、subagent artifact 在上下文中的角色
2. 再给项目证据
   - 必须回到这个项目的实现，证明这种抽象不是空想
3. 最后给教学 mock
   - 写成 OpenAI spec 风格请求体，帮助你手工构建自己的系统

这意味着：

- 我们不会脱离项目空讲概念
- 也不会陷入“只讲这个文件做了什么”的局部阅读
- 最终目标是把项目里的经验提炼成你能自己实现的上下文编译模型
